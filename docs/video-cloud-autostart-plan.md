1. **Утечка `_attempts`** — счётчики попыток оставались навсегда, если задание

размен, а не дефект — жёсткий лимит потребовал бы Durable Object. Следствие
зафиксировано в разделе 9.

## 1. Контекст

### Задача

Платформа Cloud включает autostart только на коротких видео. Замеры команды:

| Файл | Длительность | Autostart |
|------|--------------|-----------|
| 08091 | ~14 с | есть |
| 08092 | ~25 с | есть |
| 08093 | ~52 с | нет |
| 08093, обрезан | 29 с | есть |

Вывод команды: итоговый MP4 должен быть не длиннее 29 секунд.

Сейчас байер гоняет ffmpeg локально вручную, затем где-то размещает файл и
руками собирает ссылку. Задача — убрать ручную работу: загрузил видео, получил
ссылку.

### Вводные

- Исходники — до 250 МБ.
- Пользуются все пользователи вайтлиста.
- Докер не разворачиваем.
- Bot API остаётся облачный, `logOut` не делаем.

### Что уже есть в проекте

- Бот на aiogram 3.22.0, однопроцессный, `MemoryStorage`.
- Вайтлист в Google Sheets, кэш на 300 с, политика fail-closed — `utils.get_whitelist`.
- `AuthMiddleware` закрывает всё по умолчанию, кроме `/start`.
- `ThrottleMiddleware` с бакетами под операции без естественного тормоза.
- Похожий по форме флоу приёма файлов — `handlers/unicalization.py`.

### Чего нет

- `ffmpeg` на хосте.
- Файлового хранилища. `GOOGLE_DRIVE_FOLDER_ID` объявлен в `config.py:14`,
  но в коде не используется нигде — мёртвая настройка, не интеграция.
- Node-инструментов в проекте. Node 20.20.2 и npm 10.8.2 на машине есть,
  `wrangler` вызывается через `npx`, глобально ставить не требуется.

## 2. Архитектурные решения

### Решение 1. Приём файла — Telegram Mini App, заливка напрямую в R2

**Проблема:** Bot API `getFile` не отдаёт файлы больше 20 МБ. Исходники — до 250 МБ.

**Рассмотренные варианты:**

| Вариант | Вердикт |
|---------|---------|
| **Mini App + presigned PUT в R2** | ✅ **Принят.** Потолка размера нет вообще. Докер не нужен. Bot API остаётся облачным |
| Локальный Bot API server | ❌ Отклонён: единственный практичный способ поставить его — докер, а докер не разворачиваем. Сборка из исходников тянет компиляцию tdlib |
| MTProto с бот-токеном (Telethon) | ❌ Не подтверждён источниками. Гарантированно работает только юзер-аккаунт, а это session-файл = полный доступ к личному аккаунту |
| ffmpeg.wasm в браузере | ❌ Проверено: ~12× медленнее нативного, потолок памяти ~2 ГБ, нужны заголовки COOP/COEP. На 250 МБ и на телефоне не тянет |
| Google Drive как приёмник | ❌ Интеграции нет, писать с нуля, UX в два шага |
| Смириться с 20 МБ | ❌ Не покрывает заявленные 250 МБ |

**Ключевой факт, определивший выбор:** ffmpeg обязан работать на хосте при
**любом** варианте — браузер его нативно не умеет. Поэтому вопрос стоял не
«хост или облако», а только «как доставить файл на хост».

### Решение 2. Фича живёт внутри существующего процесса бота

Ни отдельного сервиса, ни контейнера.

- ffmpeg вызывается через `asyncio.create_subprocess_exec` — event loop не
  блокируется, бот остаётся отзывчивым во время транскода. Блокировал бы только
  синхронный `subprocess.run`.
- Опросчик очереди — фоновая `asyncio.Task`, стартует вместе с ботом.
- Переиспользуются вайтлист, обе middleware, FSM, клавиатуры.
- Нагрузка ограничивается семафором и `nice`, а не границей процесса.

### Решение 3. Хранилище и очередь — Cloudflare R2

- R2 отдаёт файл байт в байт. Cloudflare Stream отпадает: он перекодирует
  загруженное своим энкодером, что уничтожает смысл нашего транскода.
- S3-совместимый API, доступ через `boto3`.
- Поддерживает Range-запросы — обязательно для `<video>`.
- Egress бесплатный, поэтому скачивание 250 МБ обратно на хост ничего не стоит.

**Очередью служит сама папка `incoming/`.** Отдельного брокера нет. Ключ
объекта — `incoming/<user_id>/<uuid>.mp4`, где `user_id` подставляет Worker
после проверки подписи. Подделать нельзя, и бот сразу знает, кому отвечать.

Одиночный PUT в R2 атомарен: объект появляется в листинге только целиком.
Гонки с недозалитым файлом нет. Потолок одиночного PUT — единицы гигабайт,
250 МБ проходит без multipart.

### Решение 4. Ограничение частоты — два уровня

Загрузка идёт мимо бота, поэтому `ThrottleMiddleware` её не видит. Лимиты
разносятся:

| Уровень | Что ограничивает | Чем |
|---------|------------------|-----|
| Worker | выдачу разрешений на загрузку | счётчик в KV, 5 на пользователя в час |
| Бот | одновременные транскоды | `asyncio.Semaphore(2)` + `nice -n 19` |
| `ThrottleMiddleware` | нажатия кнопки меню | новый бакет `video_cloud` |

## 3. Схема

```
┌─ CLOUDFLARE ─────────────────────────────────────────────┐
│  Pages    — статическая страница Mini App                 │
│  Worker   — проверка подписи, вайтлист, presigned PUT     │
│  KV       — вайтлист + счётчики частоты                   │
│  R2       — incoming/ (очередь), v/ (результаты)          │
└───────────────────────────────────────────────────────────┘
        ▲ PUT из браузера      │ бот забирает / кладёт
        │                      ▼
┌─ ХОСТ ────────────────────────────────────────────────────┐
│  Процесс бота (тот же, что сегодня)                       │
│    ├── хендлеры                                            │
│    └── фоновая задача: опрос → ffmpeg → заливка → ответ    │
└───────────────────────────────────────────────────────────┘
```

Входящих соединений на хост нет ни одного. Бот ходит только наружу.

### Поток

1. Юзер жмёт «🎬 Видео для Cloud» → бот шлёт кнопку, открывающую Mini App
2. Страница открывается внутри Telegram, читает `Telegram.WebApp.initData`
3. Страница шлёт initData в Worker. Worker проверяет HMAC-подпись, сверяет
   `user_id` с вайтлистом в KV, проверяет лимит частоты, выдаёт presigned PUT
   на ключ `incoming/<user_id>/<uuid>.mp4` со сроком 5 минут
4. Браузер льёт файл напрямую в R2 — мимо хоста, мимо Telegram
5. Фоновая задача бота каждые 5 с смотрит `incoming/`. Нашла объект —
   скачала, прогнала ffmpeg, проверила результат, залила в `v/`, исходник удалила
6. Бот пишет юзеру: ссылка + сам готовый файл (~9 МБ, в лимит отправки влезает)

## 4. Что будет построено

### Фаза 0 — инфраструктура (выполняет разработчик)

Детали — раздел 7.

### Фаза 1 — `cloudflare/worker.js` (новый)

- Проверка `initData`: `secret_key = HMAC_SHA256("WebAppData", <токен бота>)`,
  затем сверка `hash` по `data_check_string`
- Проверка `auth_date` — отбой, если старше часа
- Сверка `user_id` с вайтлистом в KV
- Счётчик частоты в KV
- Выдача presigned PUT: ключ с `user_id`, TTL 5 минут, зашитые потолок размера
  и `Content-Type`
- `wrangler.toml`: привязки R2 и KV, секреты

### Фаза 2 — `cloudflare/index.html` (новый)

Одна страница: `telegram-web-app.js`, выбор файла, показ прогресса заливки,
понятные сообщения об ошибках. Тема Telegram через CSS-переменные.

### Фаза 3 — `services/video.py` (новый)

| Функция | Назначение |
|---------|-----------|
| `probe(path)` | ffprobe → длительность, ширина, высота, кодек, размер, наличие аудио |
| `transcode(src, dst)` | ffmpeg по согласованной команде, под семафором, с таймаутом |
| `verify_output(path)` | ffprobe результата: длительность ≤ 29 с, profile baseline, pix_fmt yuv420p |
| `has_faststart(path)` | скан атомов MP4: `moov` расположен раньше `mdat` |
| `VideoError` | доменное исключение с командой, кодом возврата и хвостом stderr |

Команда ffmpeg — ровно согласованная:

```
ffmpeg -nostdin -hide_banner -loglevel warning -y \
  -i input.mp4 \
  -map 0:v:0 -map 0:a? -sn -dn \
  -vf "scale='min(720,iw)':-2" \
  -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p \
  -preset medium -crf 23 -maxrate 2500k -bufsize 5000k \
  -movflags +faststart -t 29 \
  -c:a aac -b:a 128k \
  -map_metadata -1 \
  output_cloud_autostart.mp4
```

Ограничения: `asyncio.Semaphore(2)`, таймаут по стенным часам с `kill -9`,
запуск через `nice -n 19`.

`verify_output` и `has_faststart` — не формальность. Молча отдать ссылку на
файл, не соответствующий требованиям Cloud, хуже чем упасть: байер зальёт его в
рекламу и будет искать, почему autostart не работает.

### Фаза 4 — `services/r2.py` (новый)

- `list_incoming()`, `download(key, path)`, `upload(path, key)`, `delete(key)`
- `boto3` в `run_in_executor` — клиент синхронный
- Ключ результата: `v/<uuid4>.mp4`. Последовательные имена перебираются, а это
  креативы команды
- **`ContentType="video/mp4"` задаётся явно.** Без него R2 отдаст
  `application/octet-stream`, браузер не проиграет файл инлайн, и цель фичи не
  достигнута при технически успешной загрузке
- Ретраи на сетевых ошибках, затем честное исключение

### Фаза 5 — `services/video_queue.py` (новый)

Фоновая задача: опрос `incoming/` раз в 5 с → обработка → ответ юзеру.

Счётчик попыток на объект. После 3 неудач объект переносится в `failed/` и
юзеру уходит сообщение. Без этого файл, стабильно роняющий ffmpeg, крутится в
цикле вечно.

### Фаза 6 — правки существующих файлов

| Файл | Изменение |

| `keyboards.py` | кнопка «🎬 Видео для Cloud» с `WebAppInfo` в оба меню |
| `middlewares/throttle.py` | бакет `video_cloud` |
| `main.py` | старт фоновой задачи |
| `config.py` | переменные R2 и Worker |
| `requirements.txt` | `boto3` |
| `handlers/video_cloud.py` | новый: кнопка и сообщения статуса |

Существующая логика не меняется нигде. Только добавления.

## 5. Негативные пути

| Ситуация | Поведение |
|----------|-----------|
| Подпись initData не сошлась | Worker отдаёт 403, presigned URL не выдаётся |
| initData старше часа | 403 |
| `user_id` не в вайтлисте | 403 |
| Превышен лимит частоты | 429 с понятным текстом |
| Заливка брошена на середине | Объект не появится: PUT атомарен |
| Presigned URL просрочен | Браузер получает ошибку, страница предлагает повтор |
| Залили не видео | `ffprobe` не распарсит → `failed/`, юзеру сообщение |
| Видео без звука | `-map 0:a?` покрывает: `?` делает поток необязательным |
| Видео короче 29 с | Транскодируем как обычно, `-t 29` ничего не режет |
| Вертикальное 1080×1920 | `scale='min(720,iw)':-2` → 720×1280, корректно |
| `ffmpeg` упал | 3 попытки → `failed/`. В лог: команда, код возврата, хвост stderr |
| Транскод завис | Убить по таймауту, временные файлы подчистить |
| `verify_output` не прошёл | Ссылку не отдавать. Ошибка с указанием провалившейся проверки |
| R2 недоступен | Ретраи, затем честная ошибка. Файл не терять молча |
| Бот перезапустился во время обработки | Объект остался в `incoming/`, подхватится следующим циклом |
| Третий одновременный транскод | Ожидание на семафоре |
| Диск заполнен | Проверка свободного места перед скачиванием, отказ заранее |
| Брошенные объекты в `incoming/` | Lifecycle-правило R2 на префикс: удаление старше суток |

По правилу «fail loud» из глобального контракта: ни одного `except: pass`.
Каждая ошибка несёт команду, код возврата и хвост stderr.

## 6. Безопасность

| Пункт | Решение |
|-------|---------|
| Аутентификация | Подпись `initData` от Telegram. Ни паролей, ни сессий, ни своей формы логина |
| Токен бота в Worker | **Не кладём.** Только производный `HMAC_SHA256("WebAppData", token)`. Проверять подпись им можно, восстановить токен — нельзя |
| Повтор перехваченной initData | Проверка `auth_date`, отбой старше часа. Подпись сама по себе бессрочна |
| Проверка подписи | На каждом запросе, не только при открытии страницы |
| Авторизация | Вайтлист в KV, синкает бот. Та же политика fail-closed, что у `AuthMiddleware` |
| Ключи R2 | Только в секретах Worker и в `.env` бота. В JS страницы их нет никогда |
| Скоуп токена R2 | Один бакет, не весь аккаунт |
| Злоупотребление заливкой | Потолок размера и `Content-Type` зашиты в presigned-политику, TTL 5 минут, лимит частоты в KV |
| Имена объектов | `uuid4`, не последовательные |
| Публичность бакета | Ссылка открыта любому, кто её знает. Для креативов согласовано |
| Исчерпание CPU | Семафор 2 + `nice -n 19` |
| Исчерпание диска | Удаление в `finally` + проверка перед скачиванием |
| ffmpeg как поверхность атаки | Парсинг чужих медиа исторически даёт RCE. Риск снижен тем, что залить может только вайтлист — своя команда, а не интернет. Полный sandbox признан избыточным |
| PII | `initData` содержит `user_id`, username и имя. В логи — только `user_id` |

## 7. Инфраструктура: пошагово

### 7.1 Хост

```bash
apt install -y ffmpeg && ffmpeg -version
```

Проверить свободное место: при 250 МБ на файл и двух параллельных нужен запас
порядка 5 ГБ.

Докер не требуется. `logOut` не делаем — Bot API остаётся облачным.

### 7.2 Cloudflare R2

1. Дашборд → R2 → активировать (нужна привязка способа оплаты даже для
   бесплатного лимита)
2. Create bucket, например `creatives`
3. R2 → Manage API Tokens → Create API token:
   - права **Object Read & Write**
   - скоуп — **только этот бакет**
   - записать `Access Key ID`, `Secret Access Key`, эндпоинт
     `https://<account_id>.r2.cloudflarestorage.com`
4. Бакет → Settings → Custom Domains → привязать `cdn.<вашдомен>`
5. Бакет → Settings → CORS: разрешить `PUT` с домена страницы Pages
6. Бакет → Settings → Object lifecycle rules:
   - префикс `incoming/` — удаление старше 1 дня
   - префикс `v/` — удаление старше 30 дней

### 7.3 Cloudflare KV

Дашборд → Workers & Pages → KV → Create namespace, например `video_acl`.

### 7.4 Деплой Worker и Pages

Код даю я, деплой командами:

```bash
npx wrangler deploy                      # Worker
npx wrangler pages deploy cloudflare/    # страница
```

Секреты Worker (не в git):

```bash
npx wrangler secret put TG_SECRET_KEY    # производный ключ, не токен бота
npx wrangler secret put R2_ACCESS_KEY_ID
npx wrangler secret put R2_SECRET_ACCESS_KEY
```

### 7.5 BotFather

Bot Settings → Menu Button → URL страницы Pages.

### 7.6 Новое в `.env`

```
R2_ACCOUNT_ID=
R2_ACCESS_KEY_ID=
R2_SECRET_ACCESS_KEY=
R2_BUCKET=
R2_PUBLIC_BASE_URL=
```

## 9. Известные ограничения

**Бот должен оставаться однопроцессным.** Опросчик берёт задания из `incoming/`
без блокировок. Два инстанса подхватят один объект дважды. Это согласуется с
текущим состоянием (`MemoryStorage`, счётчики троттлинга в памяти процесса), но
при масштабировании потребует аренды заданий.

**Лимит частоты в Worker приблизительный.** Счётчик лежит в KV, а KV
согласован в конечном счёте: при параллельных запросах пользователь получит не
5 ссылок в час, а порядка 10. Это защита от злоупотребления объёмом, а не
граница безопасности. Жёсткий лимит требует Durable Object и признан
избыточным для внутреннего инструмента команды.

**Состояние опросчика живёт в памяти процесса.** `_in_flight` и `_attempts`
теряются при перезапуске бота. Последствия ограниченные: задание останется в
`incoming/` и будет подобрано заново, счётчик попыток начнётся с нуля. То есть
перезапуск бота даёт битому файлу лишний цикл попыток, но не бесконечный.

## 10. Открытые вопросы

### 10.1 Порог 29 секунд не проверен на изоляцию переменных

**Это принятый риск, а не упущение.**

Обрезка 52 с → 29 с изменила одновременно длительность **и** размер файла
(~16 МБ → ~9 МБ при 2500k). Какая из двух величин включает autostart — не
установлено.

Предлагавшаяся проверка (не выполнена): сжать исходные 52 секунды до ~5 МБ, не
обрезая. Autostart появится — значит лимит по размеру, и резать креативы не
нужно вовсе.

Также неизвестен точный порог между 29 и 52 секундами — возможно, 30, 35 или 40.

**Принятое решение:** реализуем `-t 29`, как задано изначально. Риск: часть
креативов обрезается без необходимости. Если проверка позже покажет, что дело в
размере — правка на одну строку, архитектуру не затрагивает.
