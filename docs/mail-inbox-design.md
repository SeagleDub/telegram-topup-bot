# Почта доменов: info@<domain> → бот

Статус: **код написан и проверен ревью, ожидает запуска (раздел 8)**.
План и правки по ревью: `docs/mail-inbox-plan.md`.
Тип работы: new feature.

## 1. Задача

Есть CSV: колонка 1 — `<email аккаунта Cloudflare>:<токен>`, колонка 3 — домен
в этом аккаунте. Для каждого домена нужен адрес `info@<domain>`, а письма на
него должны быть видны пользователям бота.

Решения, принятые с заказчиком:

| Вопрос | Решение |
|--------|---------|
| Кто читает почту | Все из вайтлиста, любой домен — как SMS Google Ads |
| Как доставлять | По запросу: список писем + «🔄 Обновить». Без пуш-уведомлений |
| Домен уже с почтой / info@ занят | Не трогать, показать в отчёте |
| Хранилище | Отдельный Worker + приватный R2-бакет |

Отклонённый вариант — пересылка всех писем в один ящик. Cloudflare требует
подтвердить адрес назначения отдельно в каждом аккаунте (письмо со ссылкой на
каждый аккаунт), пересылка ломает SPF/DMARC, а боту всё равно понадобился бы
IMAP-опросчик.

## 2. Как это устроено

```
письмо на info@site1.com
  → mail-inbox-relay        Worker в аккаунте site1.com (копия в каждом аккаунте из CSV)
  → POST /ingest            токен записи
  → mail-inbox              центральный Worker в основном аккаунте
  → R2-бакет mail-inbox     приватный, письма старше 30 дней удаляются сами
  ← бот: GET /messages      токен чтения
```

Воркеров два, потому что Cloudflare отдаёт письмо только Worker'у **того же
аккаунта**, где находится домен. Центральный Worker живёт в другом аккаунте,
поэтому в каждом аккаунте из CSV стоит маленький пересыльщик.

Путь одного письма:

1. Google шлёт код на `info@site1.com`.
2. Cloudflare аккаунта site1.com видит правило «info@ → mail-inbox-relay» и
   отдаёт письмо пересыльщику.
3. Пересыльщик отправляет письмо в `mail-inbox`.
4. `mail-inbox` кладёт его в R2, в папку `info@site1.com/`.
5. Байер в боте: «📧 Почта доменов» → `site1.com` → список → нажимает на письмо →
   бот скачивает его, превращает в текст и показывает.

### Папки

```
mail-inbox/
  collector/          центральный Worker (wrangler), деплой один раз
  relay/relay.mjs     пересыльщик; заливает скрипт через API, не wrangler
  setup/setup_routing.py   CSV → настройка аккаунтов (+ тесты рядом)
  README.md           развёртывание и запуск
  .gitignore          *.csv
handlers/mail_inbox.py      флоу в боте
services/mail_inbox.py      HTTP-клиент к mail-inbox + разбор писем
```

Раздел бота лежит в `handlers/` и `services/`, а не в `mail-inbox/`: бот
подключает модули оттуда. С почтовой системой он говорит только по HTTP — так же,
как с API luboydomen. Граница проходит по API, а не по папке.

`video-cloud` (`cloudflare/`) не меняется.

## 3. Пересыльщик: `mail-inbox-relay`

Один файл `relay/relay.mjs`, только обработчик `email()`. Письмо не разбирает.
Расширение `.mjs` — чтобы Node в тестах считал файл ES-модулем без
отдельного package.json.

- Читает письмо целиком (`message.raw`, до 25 МиБ — лимит Email Routing) и шлёт
  `POST {INGEST_URL}` с заголовками:
  - `Authorization: Bearer {RELAY_TOKEN}`;
  - `X-Mail-Meta` — `encodeURIComponent(JSON.stringify({to, from, subject}))`:
    `to` — адрес получателя (`message.to`), `from` — заголовок письма
    («Google <no-reply@…>»), а не адрес конверта: в конверте обычно адрес для
    отказов.
- До 3 попыток, паузы 1 и 3 с. Повторяются только сбои сети и ответы 5xx:
  4xx — ошибка в самом запросе, повтор её не исправит. В конце — исключение.
- Биндинги задаёт скрипт при заливке: `INGEST_URL` (plain_text),
  `RELAY_TOKEN` (secret_text).
- Флаг совместимости `global_fetch_strictly_public`.

Почему так:

- **Ничего не разбирает.** На бесплатном плане у Worker'а 10 мс CPU, и
  документация прямо предупреждает, что тяжёлый email-обработчик падает с
  `EXCEEDED_CPU`. Пересылка — это ввод-вывод, CPU почти не тратится.
- **Метаданные в URL-кодировке.** Тема письма бывает не латиницей, а
  HTTP-заголовок пропускает только Latin-1 — `fetch` упал бы на кириллической
  теме. Если тема пришла как encoded-word (`=?UTF-8?B?…?=`), её декодирует бот.
- **Флаг `global_fetch_strictly_public`.** Если домен из CSV лежит в том же
  аккаунте, что и `mail-inbox`, без флага Cloudflare блокирует запрос
  Worker→Worker (ошибка 1042). В остальных случаях флаг ни на что не влияет.

## 4. Центральный Worker: `mail-inbox`

Проект wrangler в `mail-inbox/collector/`, деплоится в основной аккаунт (где
`video-cloud` и R2).

### Хранение

Бакет `mail-inbox`, приватный, отдельный от `videostt`. `videostt` публичный —
из него раздаются видео, почте с кодами там не место.

Ключ объекта: `<address>/<revTs>-<rand8>.eml`

- `revTs` = `9999999999999 - Date.now()`, 13 цифр. R2 отдаёт ключи по
  алфавиту, поэтому новые письма идут первыми: 10 последних — один запрос `list`
  с `limit: 10`, сколько бы писем ни накопилось.
- Из `revTs` же берётся время получения для показа. Заголовок `Date` не
  используется: его ставит отправитель, и он может быть любым.
- Тело — письмо как есть (`.eml`). Разбирает бот.
- customMetadata — `from` и `subject` (тема обрезается до 200 символов). Список в
  боте строится из них, без скачивания писем.
- Правило жизненного цикла бакета: удаление через 30 дней. Коды нужны в первые
  минуты, но иногда нужно найти старое письмо («аккаунт одобрен»). Срок
  меняется одной командой.

### API

| Кто | Запрос | Ответ |
|-----|--------|-------|
| Пересыльщик | `POST /ingest` + `X-Mail-Meta`, тело — письмо | `200 {ok:true}` |
| Бот | `GET /messages?address=info@site1.com` | `200 [{id, from, subject, receivedAt, size}]`, до 10 шт. |
| Бот | `GET /message?id=<id>` | `200`, тело — письмо (`message/rfc822`) |

- `/ingest` принимает только `RELAY_TOKEN`, чтение — только `READ_TOKEN`.
  Токены — случайные 64 hex-символа (`openssl rand -hex 32`), задаются через
  `wrangler secret put`. Сравнение за постоянное время, как в
  `cloudflare/src/index.js` (функция копируется, а не импортируется: проекты
  независимы).
- Проверки входа: адрес по шаблону `local@domain`, приводится к нижнему
  регистру; `id` по шаблону ключа (иначе 400); размер тела не больше 26 МиБ.
- Коды ответа: 400 — плохой ввод, 401 — токен, 404 — нет письма, 500 — прочее
  (подробности только в лог, наружу общий текст — как в `video-cloud`).

Почему токенов два: пересыльщики стоят в чужих аккаунтах, и утечка токена
оттуда не должна открывать чтение почты.

**Принятый риск — один `RELAY_TOKEN` на все аккаунты** (решение от 2026-09-28).
`/ingest`, в отличие от Email Routing, не проверяет SPF/DKIM/DMARC. Значит, с
утёкшим токеном можно подложить в бот поддельное письмо («от Google» с
фишинговой ссылкой) для любого домена, а утечь он может из любого аккаунта,
где у кого-то есть доступ к Workers. Принято, потому что к аккаунтам из CSV
имеет доступ только команда. Если это изменится — токен на домен:
`HMAC(RELAY_SECRET, домен)`, карта «домен → токен» в биндинге пересыльщика
(все зоны аккаунта), проверка HMAC в приёмнике. Переход — повторный запуск
скрипта.

## 5. Скрипт настройки: `setup/setup_routing.py`

```bash
.venv/bin/python mail-inbox/setup/setup_routing.py domains.csv --dry-run
.venv/bin/python mail-inbox/setup/setup_routing.py domains.csv
```

Только стандартная библиотека (`urllib`, `csv`, `json`) плюс уже
установленный `python-dotenv`. `MAIL_INBOX_URL` (скрипт сам дописывает
`/ingest`) и `RELAY_TOKEN` берутся из `mail-inbox/.env` — токена записи в
`.env` бота нет, боту он не нужен. `.env` уже
игнорируется корневым `.gitignore`, CSV игнорирует `mail-inbox/.gitignore`.

### Разбор CSV

- Разделитель — первый из символов `,` `;` табуляция в каждой строке: в
  `email:token` их не бывает. `csv.Sniffer` не годится: русский Excel пишет
  `;`, а `,` во второй колонке — десятичная запятая, и он выбирает `,`.
- Колонка 1 делится по первому `:` на email и токен, колонка 3 — домен
  (без пробелов, в нижнем регистре). Колонка 2 не используется.
- Строка без `:` в колонке 1 (например, заголовок) пропускается с пометкой.

### Авторизация

На первом запросе к аккаунту токен пробуется как API Token
(`Authorization: Bearer`). Если Cloudflare отвечает ошибкой авторизации —
как Global API Key (`X-Auth-Email` + `X-Auth-Key`). Удачный способ
запоминается для этой пары email:token. `/user/tokens/verify` не
используется: он не работает для токенов, выданных на аккаунт.

Права, которые нужны API Token (из OpenAPI-схемы Cloudflare): Zone → Zone Read,
Zone → DNS Read, Zone → Zone Settings Edit (включение Email Routing),
Zone → Email Routing Rules Edit, Account → Workers Scripts Edit. У Global API
Key есть все.

### Шаги для каждого домена

1. `GET /zones?name=<domain>` → zone id, account id, статус. Домена нет →
   «не найден в аккаунте». Статус не `active` → «NS не на Cloudflare».
2. Проверка конфликтов. Любой найденный конфликт → домен пропускается, причина
   идёт в отчёт:
   - MX-записи, указывающие не на `*.mx.cloudflare.net` → «чужая почта: <хосты>»;
   - правило для `info@<domain>` с другим действием → «info@ уже пересылается:
     <куда>»;
   - корневая TXT `v=spf1…` без `_spf.mx.cloudflare.net` → «есть свой SPF».
     Вторая SPF-запись сделала бы SPF домена недействительным. Проверяется,
     только если Email Routing ещё выключен: SPF добавляет именно включение;
   - включённый catch-all с действием не `drop` → «catch-all уже настроен:
     <куда>». Он уже доставляет и info@, а правило для info@ точнее catch-all и
     молча увело бы эти письма;
   - Email Routing включён, но статус не `ready` (например, удалили MX) →
     домен не называется «настроенным»: письма туда не придут.
3. Залить пересыльщика в аккаунт — один раз на аккаунт за запуск:
   `PUT /accounts/{id}/workers/scripts/mail-inbox-relay`, multipart с
   `relay.mjs` и metadata (биндинги, флаг, compatibility_date). До изменений
   DNS: если заливка не удастся (раздел 9), домен останется нетронутым.
4. Email Routing выключен → включить (Cloudflare добавит и заблокирует MX,
   SPF, DKIM).
5. Правила для `info@<domain>` нет → создать: matcher `literal`/`to`, action
   `worker` → `mail-inbox-relay`. Наше правило есть, но выключено → включить.

`MAIL_INBOX_URL` с `/ingest` на конце скрипт исправляет сам: иначе все
пересыльщики слали бы на `/ingest/ingest` и теряли письма.

В `--dry-run` выполняются только чтения, вместо изменений печатается, что было
бы сделано.

### Отчёт

Консоль + `<имя входного файла>.report.csv` рядом с ним (`domains.csv` →
`domains.report.csv`, чтобы отчёт не перезаписал сам CSV): домен, статус, причина.
Статусы: ✅ настроен · ↩️ уже был настроен · ⏭ пропущен · ❌ ошибка (текст
Cloudflare, например нехватка прав). Токенов в выводе и отчёте нет.

### Почему так

- **Повторный запуск безопасен.** Настроенные домены — «↩️ уже был настроен».
  Пересыльщик перезаливается, так что обновить его код во всех аккаунтах = запустить
  скрипт ещё раз.
- **Последовательно, без параллельности.** Лимит Cloudflare — 1200 запросов за
  5 минут, на домен уходит ~6 запросов. Сотни доменов проходят за минуты, а
  вывод читается по порядку.
- **Нет флага «только один домен».** Для теста хватает CSV из одной строки.

## 6. Бот

### Флоу

1. Кнопка «📧 Почта доменов» — в обоих меню (`menu_kb_user`,
   `menu_kb_with_buyer_expenses`).
2. «Введите домен» (`cancel_kb`), состояние `Form.mail_waiting_for_domain`.
   Ввод приводится к адресу: `site1.com`, `INFO@Site1.com`,
   `https://www.site1.com/page` → `info@site1.com`. Если введён адрес с другой
   частью до `@`, берётся как есть.
3. Список: заголовок `📬 info@site1.com` + до 10 инлайн-кнопок
   `12:41 · Google · Подтвердите адрес…` (для писем не за сегодня —
   `26.09 12:41`) + «🔄 Обновить». Писем нет → «Писем пока нет» + «🔄 Обновить».
4. Нажатие на письмо → сообщение: тема, от кого, время получения (Europe/Kyiv, как
   в `services/ecards.py`), текст, список вложений по именам.

### Детали и почему

- **callback_data** — `mail:open:<n>` и `mail:refresh`, а адрес и id писем
  хранятся в FSM. Telegram ограничивает данные кнопки 64 байтами, id с длинным
  доменом туда не влезает. Бот перезапустился и забыл список (MemoryStorage) →
  «Список устарел, введите домен ещё раз».
- **Превью ссылок выключены** (`disable_web_page_preview=True`, как в
  `services/video_queue.py`). Для превью Telegram сам открывает ссылку, и
  одноразовая ссылка «войти / подтвердить» сработала бы раньше человека.
- **Разбор письма** — стандартный `email` (`policy.default`),
  `get_body(preferencelist=("plain", "html"))`. HTML → текст через
  `html.parser`, адрес ссылки остаётся рядом с её текстом:
  `Подтвердить (https://…)` — в письмах с подтверждением главное часто в кнопке.
  Кодировки (cp1251, quoted-printable, base64) разбирает сам модуль `email`.
- **Весь текст из письма экранируется** (`html.escape`) перед отправкой с
  `parse_mode="HTML"`: содержимое письма чужое.
- **Длина** — считается в единицах UTF-16, как в Telegram (лимит 4096 на
  сообщение, эмодзи — две единицы): текст — до 3000 с пометкой «…обрезано»,
  тема и отправитель — до 200, список вложений — до 300. Если Telegram всё же
  отклонит сообщение, человек получит короткий отказ, а не тишину.
- **Пустой text/plain** — показывается HTML-часть: бывает, что код только в ней.
- **Вложения** не пересылаются, только имена.
- **Троттлинг** — бакет `mail` (10 запросов в минуту, как `sms`) для кнопки
  меню и callback'ов с префиксом `mail:`.
- **Ошибки.** Приёмник недоступен или ответил 5xx/401 → «❌ Почта сейчас
  недоступна, попробуйте через минуту», подробности в `logger.exception`.
  Письмо не разобралось → показываем заголовки и «не удалось разобрать текст».
- **Не настроено.** Нет `MAIL_INBOX_URL` или `MAIL_READ_TOKEN` в `.env` →
  предупреждение в лог на старте, кнопка отвечает «функция не настроена» (тот же
  подход, что у «Видео для Cloud»).

## 7. Проверки

**Python** (`tests/test_mail_inbox.py`, unittest, как существующие тесты):
- ввод → адрес (варианты из п. 6, мусор → ошибка);
- письмо в cp1251 + quoted-printable;
- HTML-письмо: ссылки сохраняются;
- тема как encoded-word;
- обрезка длинного текста;
- список вложений.

**Python, скрипт** (`mail-inbox/setup/test_setup_routing.py` — рядом со
скриптом, подсистема остаётся в своей папке): решение «настраивать /
пропустить» на заготовленных ответах API (чужие MX, свой SPF, занятый info@,
уже настроенный домен), разбор CSV, тело заливки пересыльщика.

**JS** (`node --test`, как `cloudflare/test/`):
- `revTs`: письмо, пришедшее позже, идёт в списке раньше;
- неверный токен → 401, токен записи не даёт читать;
- пересыльщик: 3 попытки, потом исключение; успех со второй попытки.

**Вживую, на одном тестовом домене** — на зоне, где Email Routing никогда не
включали: так проверяются ответы API на «свежей» зоне, которые офлайн не
проверить.
1. `--dry-run` → запуск → письмо из Gmail → видно в боте.
2. Письмо с кириллической темой и HTML-кнопкой.
3. Сломать `RELAY_TOKEN` → отправить письмо → посмотреть, что Cloudflare сделал с
   письмом (см. п. 9).

## 8. Порядок запуска

1. `npx wrangler r2 bucket create mail-inbox` + правило удаления через 30 дней.
2. Деплой `mail-inbox/collector`, `wrangler secret put RELAY_TOKEN` и
   `READ_TOKEN`.
3. Бот: 2 строки в `.env` (`MAIL_INBOX_URL`, `MAIL_READ_TOKEN`), перезапуск.
4. Один тестовый домен — проверки из п. 7.
5. `--dry-run` по всему CSV → разбор отчёта → настоящий запуск.

Оценка: ~5–6 ч с тестами (приёмник и пересыльщик ~1,5 ч, скрипт ~2 ч, бот
~2 ч) + ~30 мин живой проверки.

## 9. Проверить на тестовом домене до массового запуска

Документация Cloudflare на эти вопросы явно не отвечает:

1. Что происходит с письмом, если пересыльщик упал: отправитель получит
   временную ошибку и повторит (письмо придёт позже) или письмо потеряется.
   Если потеряется — обсудить запасной вариант до массового запуска.
2. Как API включения Email Routing ведёт себя при существующем SPF. До проверки
   это конфликт и домен пропускается (п. 5).
3. ~~Минимальные права API Token~~ — закрыто: список в разделе 5, взят из
   OpenAPI-схемы Cloudflare.
4. Заливается ли Worker в аккаунт, где Workers ни разу не использовались (нужен
   ли поддомен workers.dev).

## 10. Не делаем сейчас
